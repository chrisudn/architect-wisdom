# 康威定律實戰：系統架構背後的權力地盤與責任隔離

> **「任何組織在設計系統時，其架構樣式必然會反映出該組織內部的溝通與權力結構。」 —— 康威定律（Conway's Law）**

---

## 一、 系統架構圖：組織權力的冷酷投影

很多工程師以為架構是純粹客觀的數學與工程優化產物。然而，當你退後一步，從組織的人文與政治視角審視任何一套微服務架構時，你會發現：

**系統拓撲圖上的每一個方框，都是部門與個人的權力地盤；連接方框的每一條線，都是組織利益博弈後的妥協。**

* 為什麼這個模組不放在服務 A，而要單獨拆出服務 B？因為兩個組由不同的經理管轄；
* 為什麼這個介面要採用非同步佇列解耦？因為上游團隊不願為下游的崩潰承擔責任；
* 為什麼會有死信佇列補償？因為在出事時，必須有一份不可抵賴的審計記錄來證明「我已經發送了，是對面沒處理好」。

---

## 二、 單體的「無限連坐」vs 拆分的「封建領地」

從防禦性組織學的角度來看，架構選型直接決定了你的**政治生存風險**：

### 1. 單體架構的政治死穴：無限連坐背黑鍋
在單體架構中，所有團隊的代碼都打包在同一個 `.jar` 或同一個容器中運行。這在組織政治上意味著**「連坐法」**：
* 隔壁組的新人在一個不重要的邊緣功能裡寫了個死循環或內存洩漏；
* 整個單體服務崩潰，核心交易全線中斷；
* 在高層召開的跨部門事故檢討會上，老闆只會震怒：「為什麼整個系統會癱瘓？今天值班負責人是誰？」
* 你就算程式碼寫得再完美，也必須跟著整個團隊一起吃考核降等。**在單體裡，你永遠在替最差的隊友承擔連帶責任。**

### 2. 領域拆分的防禦本質：爆炸半徑（Blast Radius）與地盤防火牆
當你將系統按業務領域拆分為多個自治服務時，你實質上在組織內部完成了**「封建領地劃分」**：
* **邊界即防火牆**：即使外圍的遊戲或非核心業務被流量衝垮，核心數據管道依然安然無恙；
* **責任鏈路涇渭分明**：監控儀表板上的錯誤代碼、HTTP 狀態與 MQ 佇列堆積會明確指向出問題的具體服務。**這不是為了甩鍋，而是為了建立清晰的權責邊界，防止組織內耗與平庸連坐。**

---

## 三、 跨部門協同的摩擦係數管理

當系統被拆分為多個服務後，最嚴峻的挑戰轉移到了**「跨部門協同」**上。

### 1. 拒絕跨專案 Jar 檔依賴（避免隱性地盤侵入）
微服務開發中最容易犯的政治錯誤，就是搞一個「全公司共用的 `common.jar`」：
* 只要有一個團隊隨意升級了 common 裡的一個依賴版本，其他所有服務在編譯或部署時全部跟著遭殃；
* **嚴禁跨專案引用 Java Class，改為嚴格基於 JSON Schema / REST / MQ 契約傳輸。** 讓各自的領域在代碼層面徹底獨立，確保地盤的純粹性。

### 2. 被依賴方與調用方的心理防線
在跨服務協調中，老謀士的黃金法則：
* **「下游先行（被依賴方優先）」**：當其他團隊要調用你的服務時，永遠先拍板輸入輸出 Schema，讓對方先以 Mock 方式開發；
* **「防脆性隔離」**：任何對外部服務的 HTTP 呼叫，必須配置嚴格的連線/讀取超時（Connect/Read Timeout）與 Try-Catch/Fallback 機制。**永遠不要假設外部系統是可靠的，對外防禦，對內自治。**
